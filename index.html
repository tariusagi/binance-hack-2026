04 // fund status (as of 30 Oct)

Where the $6.3B sits

frozen ~$3.0B unfreezable BTC $1.5B with attackers $1.8B
Per the status table reported in Wikipedia. Attackers spread funds across roughly 12,000 wallets (Elliptic). As of 30 Oct none had been converted to fiat.

Frozen-amount estimates

Binance ~$3.0B · Chainalysis ~$2.8B · TRM Labs ~$2.7B. Binance also said it had frozen or intercepted up to $2.9B (Forbes).
Why it matters: stablecoins are freezable by issuers (Tether, Circle). Native BTC is not, which explains why the $1.5B BTC leg is the unrecoverable core of the loss unless the attackers move it through a freezable rail.

06 // attack vector (as reported, not yet a full post-mortem)

STAGE 01
Recruitment lure
A Binance software engineer is contacted by "a person posing as a Project Director" via a job platform, with fake interviews and video calls.
STAGE 02
Malware on workstation
Malicious code gives remote access to the engineer's laptop, with the ability to deploy software.
STAGE 03
Internal AI tool abused
A compromised internal AI tool is reportedly used to reach the wallet-signing service.
STAGE 04
Hot-wallet authority abused
Attackers grant network permissions directly on Ethereum (EIP-7702 delegation, per CEO Richard Teng via BBC), so halting withdrawals did not stop the drain.
STAGE 05
Multi-chain drain
~20 min across 10 chains; ~12,000 wallets used to dilute freezes.
Binance says its investigation "uncovered additional points of breach" beyond the initial laptop. TRM Labs says preparation started at least 36 hours before the theft. No full technical post-mortem has been published as of this writing. Treat the stages above as reported, not confirmed.

06b // EIP-7702 (the mechanism named in the reporting)

What it is

EIP-7702 is an Ethereum core standard (status: Final, created 7 May 2024) that lets a normal key-controlled account, an externally owned account (EOA), temporarily run smart-contract code. Before it, an EOA had no code: a single private-key signature was the only way to authorise its actions. The spec adds a new transaction type, 0x04, carrying an authorization list. Each entry tells the chain "this account's code is now the code at address X".

The spec page does not name an activation fork. EIP-7702 is commonly associated with the Pectra upgrade in 2025; verify against the spec's network-upgrade notes before relying on that date.

Authorization tuple

chain_ida specific chain, or 0 = valid on any chain
addresscontract whose code the EOA will adopt
noncemust match the EOA's nonce, then increments
y_parity, r, ssignature by the EOA's own key

The signature covers keccak256(0x05 || rlp([chain_id, address, nonce])). Anyone who obtains a valid tuple can submit it in their own transaction, and the sender pays the gas.

Key constants

NameValueMeaning
SET_CODE_TX_TYPE0x04new transaction type
MAGIC0x05prefix for signed authorization hash
PER_AUTH_BASE_COST12,500gas per tuple
PER_EMPTY_ACCOUNT_COST25,000gas charged per tuple, refund on use
Delegation indicator0xef0100 + address23-byte code the EVM follows

Processing rules (as specified)

  • Tuples are checked one by one. Invalid tuples are skipped; if an address appears twice, the last valid entry wins.
  • The account must have empty code or an existing delegation. Accounts with other code cannot delegate.
  • A failed transaction does not undo delegations already processed.
  • The sender pays for every tuple, valid or not.
  • Revocation: delegating to the zero address clears the indicator and restores empty code.

Why it matters for this incident

Once an attacker holds a valid signature from a hot-wallet key, they can make that address run attacker-chosen code. That code can move every asset the account controls, on every chain where the tuple is accepted. Stopping withdrawals in Binance's own system does not block this, because the authority sits on-chain: this matches Binance's account that halting withdrawals did not stop the drain (see 06).

Correction to the reporting: the Wikipedia summary attributes a "multi-signature protocol called EIP-7702" to CEO Richard Teng (via BBC). EIP-7702 is not a multisig protocol. It is account-code delegation: one valid key signature can grant an address a contract's behaviour. Whether the attackers used a wildcard chain_id, a particular delegate contract, or a pre-signed tuple has not been published in a full post-mortem.

Phishing and drainer risk

The spec has no phishing section. Its rationale says applications must not ask users to sign authorisations, and that "there is no safe way to provide this interface" because few users can verify the code they delegate to.

Reported post-Pectra uses by drainers: a MetaMask user lost about $146.6K on 24 May 2025 to a batched EIP-7702 transaction tied to Inferno Drainer, and Scam Sniffer reported two large cases in August 2025. Other reporting argues the risk is overstated, since the attacker still needs a signature, and that the real gap is wallets that show the signature as generic.

Sources differ on scale. The vendor-sourced figures are not independently audited.

Practical safeguards

  • Never sign an authorisation request you cannot read: check the target address and the chain.
  • Be wary of any tuple with chain_id 0, which works across all chains.
  • Wallets should display the delegate contract and nonce, and simulate it before signing.
  • Operators of hot wallets should treat every signing key as one that can hand over full control, and monitor delegation indicators on their accounts.
  • To remove a delegation, send a new authorisation pointing to the zero address.
